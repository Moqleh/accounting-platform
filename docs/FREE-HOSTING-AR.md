# تجهيز الاستضافة المجانية: Render + Neon

الحالة: إعداد نشر قابل للمراجعة، وليس نشرًا فعليًا. لم يُنشأ مورد سحابي أو حساب، ولم تُنقل بيانات المتصفح. لا تُدخل بيانات حسابات حقيقية قبل اجتياز اختبار الصلاحيات أدناه.

## التكوين
- تبقى الواجهة على GitHub Pages ورابطها الحالي.
- الخادم: `deploy/render.free.yaml` يحدد خدمة Render واحدة بخطة `free`، دون قاعدة Render أو مورد مدفوع، مع نشر تلقائي معطل.
- قاعدة البيانات: مشروع Neon بخطة Free، يُنشأ بشكل منفصل في الحساب الخاص بك.
- الحدود المجانية قابلة للتغيير. خادم Render المجاني ينام عند الخمول؛ ليس هناك ضمان استمرار خدمة مجاني للأبد.
- المراجع: https://render.com/docs/free وhttps://render.com/docs/blueprint-spec وhttps://neon.com/pricing

## ما يلزم من صاحب الحساب
1. حساب Render وحساب Neon على الخطط المجانية، وربط المستودع الخاص بالخادم مع Render.
2. اختيار منطقة متقاربة للخدمتين إن كانت متاحة بالخطة المجانية.
3. اختيار بريد حساب المسؤول واسم الشركة والعملة الأساسية. بريد التواصل العام لا يصبح تلقائيًا حساب دخول.
4. أدخل أسرار قاعدة البيانات وكلمة مرور المسؤول داخل أدوات الاستضافة الآمنة فقط، وليس في GitHub أو المحادثة.

## فصل صلاحيات قاعدة البيانات — مانع تشغيل يجب حله
المراجعة الحالية أظهرت أن `AuthService.buildSession` يقرأ CompanyMembership دون سياق RLS، وبعض مسارات AdminController تستخدم Prisma مباشرة دون TenantPrismaService. مع مستخدم قاعدة بيانات محدود، قد يفشل الدخول والتهيئة. أما استخدام مالك قاعدة البيانات لتجاوز المشكلة فليس حلاً مقبولاً.

قبل تفعيل الخادم يجب:
- تصحيح تحميل العضويات بعد التحقق من كلمة المرور دون كشف عضويات مستخدم آخر.
- تنفيذ قراءات وكتابات الشركة داخل سياق tenant موثوق ومحدد للمعاملة، بما فيها مسارات الإدارة.
- اختبار تسجيل الدخول والتهيئة والترحيل بحساب قاعدة بيانات محدود فعليًا، واختبار أن شركة لا تستطيع قراءة أو تعديل بيانات أخرى.
- استخدام دور تسجيل دخول ينتمي إلى accounting_app، لا يملك الجداول ولا يحمل BYPASSRLS أو صلاحيات إدارة. أدوار Neon المنشأة من لوحة التحكم قد تملك neon_superuser؛ يجب مراجعة امتيازات الدور وعدم افتراض أنه محدود.
- مراجعة سياسة إدارة عضويات المستخدمين لتسمح لمسؤول الشركة بالإدارة المصرح بها فقط.

## تهيئة قاعدة جديدة
التنفيذ مرة واحدة فقط على قاعدة فارغة، بواسطة مسؤول القاعدة، وبعد حل مانع الصلاحيات. المشروع يستخدم حاليًا Prisma db push مع ملفات SQL إضافية؛ لا توجد سلسلة migrations كاملة. لا تُشغّل هذه الخطوات تلقائيًا عند بدء خدمة Render، ولا تستخدم --accept-data-loss أو --force-reset على بيانات موجودة.

ترتيب الإعداد الموجود في CI:
1. `pnpm --filter @accounting/api prisma:generate`
2. `pnpm --filter @accounting/api exec prisma db push --skip-generate`
3. تنفيذ الملفات التالية بواسطة psql مع `ON_ERROR_STOP=1` وبالترتيب: `security.sql`، ثم `banking.sql`، ثم `posting-config.sql`، ثم `purchase-returns.sql`، من apps/api/prisma.
4. إنشاء المسؤول الأول عبر `prisma:bootstrap` باستخدام BOOTSTRAP_ADMIN_EMAIL وBOOTSTRAP_ADMIN_PASSWORD وBOOTSTRAP_COMPANY_NAME وBOOTSTRAP_BASE_CURRENCY. لا تستخدم seed التجريبي لبيانات العمل.
5. اختبار حساب API محدود الصلاحيات قبل وضع DATABASE_URL الخاص به في Render.

رابط الاتصال الإداري المباشر يبقى منفصلاً عن رابط تشغيل التطبيق. احتفظ بـ SSL وفق رابط Neon، ولا تحذف خيارات TLS. Prisma يستخدم DATABASE_URL؛ لا تضعه في NEXT_PUBLIC_API_URL.

## نشر الخادم
بعد اجتياز ما سبق، أنشئ Blueprint من deploy/render.free.yaml. تحقّق في ملخص Render من أن الخطة Free قبل الإنشاء. أدخل DATABASE_URL للدور المحدود. JWT_SECRET يُولّد تلقائيًا وCORS_ORIGINS مضبوط على أصل الموقع فقط. الخدمة تستمع إلى PORT الذي تضبطه Render. لا يتضمن تشغيل الحاوية أي حذف أو إعادة إنشاء للبيانات.

Dockerfile.api الحالي هو أساس الحاوية؛ لا توجد تجربة Docker محلية موثقة في هذه الجلسة. يجب نجاح البناء على Render وفحص /api/health، ثم اختبار الدخول والعمليات الفعلية قبل تحويل الواجهة.

## تحويل الواجهة مع إمكانية الرجوع
workflow Pages يقرأ متغير المستودع ACCOUNTING_API_URL فقط عند ضبط ACCOUNTING_BACKEND_ENABLED على true. حتى ذلك الحين يستمر وضع المعاينة الحالي.
- ضع رابط الخادم العام المنتهي بـ /api في ACCOUNTING_API_URL. هذا عنوان عام وليس سرًا.
- بعد التحقق من تسجيل الدخول والمستخدمين والتهيئة والمبيعات والمشتريات والمرتجعات والتسويات والإقفال في بيئة اختبار، اضبط ACCOUNTING_BACKEND_ENABLED=true وأعد تشغيل workflow Pages.
- للرجوع إلى المعاينة، اضبط ACCOUNTING_BACKEND_ENABLED=false ثم أعد البناء والنشر.
- بيانات المتصفح التجريبية لا تُرحّل تلقائيًا إلى الخادم. استخدم جلسة دخول جديدة عند الانتقال، ولا تعتمد جلسة المعاينة على الخادم.

نجاح /api/health يثبت أن العملية تعمل فقط؛ لا يثبت صحة العزل أو اكتمال العمليات المحاسبية.
